# 프로젝트 소프트 삭제와 제외 조직 가시성 설계

## 배경

프로젝트에서 조직을 제외하면 명단·집계 이력이 있는 연결은 데이터 보존을
위해 비활성 상태로 남는다. 현재 프로젝트 조직 화면은 활성·비활성 연결을
모두 렌더링하므로 사용자는 제외 작업이 반영되지 않은 것으로 인식한다.

프로젝트도 운영 목록에서 제거할 수 있어야 한다. 다만 프로젝트에는 명단,
조직 연결, 예상 집계와 감사 이력이 연결되므로 영구 삭제보다 복구 가능한
소프트 삭제가 안전하다.

## 목표

- 프로젝트에서 제외한 조직을 활성 조직 목록에서 즉시 숨긴다.
- 제외한 조직을 조직 추가 검색에서 다시 선택해 재활성화할 수 있게 한다.
- 종료된 프로젝트를 운영자가 소프트 삭제하고 복구할 수 있게 한다.
- 삭제된 프로젝트의 운영 데이터를 보존하고 일반 운영 흐름에서는 숨긴다.
- 삭제·복구와 기존 조직 연결 변경의 동시성을 revision으로 보호한다.

## 범위 밖

- 프로젝트와 관련 데이터를 물리적으로 영구 삭제하는 기능
- 삭제된 프로젝트 데이터의 개별 수정
- 전역 조직 또는 조직 담당자의 삭제
- 휴지통 자동 비우기와 보존 기간 정책
- 조직장에게 프로젝트 삭제·복구 권한 부여

## 프로젝트 조직 제외

### 저장 동작

기존 프로젝트 조직 제외 규칙을 유지한다.

- 명단과 예상 집계 이력이 없으면 `project_organizations` 연결 행을 삭제한다.
- 명단 또는 예상 집계 이력이 있으면 연결을 비활성화하고 이력을 보존한다.
- 두 경우 모두 프로젝트 revision을 증가시키고 감사 이력을 남긴다.
- 전역 `organizations`, 조직 담당자, 다른 프로젝트 연결은 변경하지 않는다.

### 조회와 화면

프로젝트 조직 패널은 활성 프로젝트 연결만 표시한다. 전역 조직이 비활성인
경우도 활성 작업 대상으로 볼 수 없으므로 기본 목록에서 제외한다.

조직 추가 선택기의 이미 연결된 조직 집합에는 활성 연결만 포함한다.
비활성 연결은 검색 결과에 다시 나타나며 선택하면 신규 연결을 만들지 않고
기존 연결을 재활성화한다. 재활성화하면 보존된 명단·집계 이력이 다시 같은
조직에 연결된다는 안내를 표시한다.

조직장에게 반환하는 프로젝트 조직 목록도 권한 판단에 필요한 기존 연결
정보를 훼손하지 않는다. 다만 조직장 UI의 작업 대상에는 활성 프로젝트
연결과 활성 전역 조직만 사용한다.

## 프로젝트 소프트 삭제

### 상태 모델

기존 프로젝트 업무 상태 `PRE_REGISTRATION`, `IN_PROGRESS`, `CLOSED`는
변경하지 않는다. `DELETED`를 업무 상태에 추가하지 않고 다음 nullable
메타데이터로 삭제 여부를 표현한다.

- `deleted_at`: 삭제 시각
- `deleted_by`: 삭제한 운영자 ID
- `deleted_revision`: 삭제 요청이 성공한 뒤의 프로젝트 revision

삭제 가능한 프로젝트는 `CLOSED` 상태이며 아직 삭제되지 않은 프로젝트로
제한한다. 수동 종료와 자동 종료를 구분하지 않는다.

삭제 시 프로젝트 revision을 1 증가시키고 `PROJECT_DELETED` 감사 이력을
남긴다. 명단, 예상 집계, 프로젝트 조직 연결과 기존 감사 이력은 그대로
보존한다.

복구 시 삭제 메타데이터를 비우고 revision을 다시 1 증가시킨다. 업무 상태는
항상 `CLOSED`로 유지하고 `PROJECT_RESTORED` 감사 이력을 남긴다. 복구가
프로젝트를 자동으로 진행 상태로 되돌리지는 않는다.

### 권한

- 전체 운영 권한을 가진 일반 운영자만 삭제·복구할 수 있다.
- 조직장은 삭제 프로젝트를 목록·상세에서 조회하거나 복구할 수 없다.
- bootstrap 운영자는 기존 관리 작업 제한을 그대로 적용한다.

### 삭제 확인

삭제 요청은 다음 값을 받는다.

- 사용자가 입력한 프로젝트 이름
- 현재 화면이 알고 있는 `expectedRevision`

서버는 canonical 변환 없이 저장된 프로젝트 이름과 확인 이름이 정확히
일치하는지 검사한다. 공백, 대소문자 또는 유니코드 표현이 다르면 삭제하지
않는다. UI의 이름 일치 검사는 편의 기능이고 서버 검사가 최종 안전장치다.

삭제·복구는 운영자 권한, 현재 revision, 삭제 여부와 프로젝트 상태를 한
원자적 작업에서 다시 검증한다.

## API

### 프로젝트 목록

`GET /api/v1/projects`는 기본적으로 삭제되지 않은 프로젝트만 반환한다.

운영자는 `GET /api/v1/projects?includeDeleted=true`로 삭제 프로젝트를 포함할
수 있다. 조직장이 `includeDeleted=true`를 보내면 삭제 프로젝트를 반환하지
않고 권한 오류로 처리한다.

프로젝트 응답에는 운영자 화면에 필요한 다음 필드를 추가한다.

- `isDeleted`
- `deletedAt`

`deletedBy`와 내부 삭제 revision은 일반 목록 응답에 노출하지 않는다.

### 프로젝트 상세

삭제되지 않은 프로젝트의 기존 상세 조회는 그대로 동작한다. 삭제된
프로젝트는 일반 상세 조회에서 `NOT_FOUND`로 취급한다.

운영자가 삭제 목록에서 접근할 때는 명시적인 `includeDeleted=true`가 있는
상세 요청만 허용한다. 이 상세 화면은 읽기 전용이며 복구 작업만 제공한다.

### 삭제

`DELETE /api/v1/projects/:id`

요청 본문:

```json
{
  "confirmationName": "1회 수련 법회",
  "expectedRevision": 7
}
```

성공 시 갱신된 프로젝트 요약을 반환한다. 다음 오류를 구분한다.

- 프로젝트가 없거나 이미 삭제됨: `NOT_FOUND`
- 종료 상태가 아님: `PROJECT_NOT_CLOSED`
- 확인 이름 불일치: `CONFIRMATION_MISMATCH`
- revision 불일치 또는 경합: `STALE_REVISION`

### 복구

`POST /api/v1/projects/:id/restore`

요청 본문:

```json
{
  "expectedRevision": 8
}
```

삭제된 프로젝트만 복구한다. 이미 복구되었거나 존재하지 않으면
`NOT_FOUND`, revision 경합은 `STALE_REVISION`으로 응답한다.

## 화면 흐름

### 프로젝트 상세

종료되고 삭제되지 않은 프로젝트의 운영자 상세 화면에 `프로젝트 삭제`
버튼을 표시한다. 진행 중 또는 사전 등록 프로젝트에는 삭제 버튼을 표시하지
않는다.

삭제 모달은 다음 내용을 포함한다.

- 프로젝트 삭제가 목록에서 숨기는 복구 가능한 작업이라는 설명
- 보존되는 명단·조직·집계·감사 이력 안내
- 정확한 프로젝트 이름 입력란
- 취소와 삭제 버튼

이름이 정확히 일치하지 않으면 삭제 버튼을 비활성화한다. 요청 중에는 중복
제출을 막는다. 성공하면 프로젝트 목록으로 이동하고 목록 query를
무효화한다.

### 프로젝트 목록과 복구

운영자 프로젝트 목록에 `삭제된 프로젝트 포함` 필터를 둔다. 기본값은
꺼짐이며 조직장에게는 필터를 표시하지 않는다.

삭제 프로젝트 카드는 `삭제됨` 배지와 비활성 시각 스타일을 사용한다.
카드를 열면 읽기 전용 상세와 `프로젝트 복구` 버튼을 보여준다. 수정, 상태
전환, 조직 변경, 명단 변경, 가져오기와 내보내기는 제공하지 않는다.

복구 성공 후 프로젝트는 종료 프로젝트로 일반 목록에 다시 나타난다.

## 삭제 프로젝트 접근 차단

프로젝트를 참조하는 모든 기존 서비스의 공통 프로젝트 조회 경계에서
`deleted_at IS NULL`을 요구한다. 따라서 삭제된 프로젝트에 대한 조직,
참가자, 명단, 집계, 감사, 가져오기와 내보내기 요청은 일반 사용자에게
`NOT_FOUND`로 보인다.

삭제 프로젝트 전용 운영자 상세 조회와 복구 서비스만 삭제 행을 명시적으로
조회할 수 있다. Cron 자동 종료는 삭제 프로젝트를 대상에서 제외한다.

## 오류와 동시성

- 삭제 모달이 열린 뒤 프로젝트가 변경되면 삭제 요청은 `STALE_REVISION`으로
  실패하고 최신 프로젝트를 다시 불러온다.
- 다른 요청이 먼저 삭제하거나 복구하면 후발 요청은 `NOT_FOUND` 또는
  `STALE_REVISION`으로 종료하며 성공 감사 이력을 중복 생성하지 않는다.
- 조직 제외 후 상세 재조회가 실패하면 변경 성공과 재조회 실패를 구분해
  안내한다.
- 제외 조직 재추가 중 프로젝트가 종료되면 기존 `PROJECT_CLOSED` 처리를
  유지한다.
- 삭제·복구 감사 기록 실패 시 상태 변경도 함께 롤백한다.

## 마이그레이션과 기존 데이터

새 D1 migration은 `projects`에 삭제 메타데이터 열과 필요한 목록 조회
인덱스를 추가한다. 기존 행의 삭제 메타데이터는 모두 `NULL`이므로 기존
프로젝트는 그대로 노출된다.

배포 전 원격 D1 export와 checksum을 만들고 migration을 적용한다. 적용 전후
전체 프로젝트 수와 삭제되지 않은 프로젝트 수가 같아야 하며
`PRAGMA foreign_key_check`가 행을 반환하지 않아야 한다.

## 테스트

### 계약과 도메인

- 삭제·복구 요청 및 프로젝트 삭제 메타데이터 파싱
- 확인 이름의 exact match
- 삭제 가능 상태와 오류 코드

### Worker 통합 테스트

- 종료 프로젝트 삭제와 복구
- 사전 등록·진행 중 프로젝트 삭제 차단
- 삭제·복구 revision 경합과 감사 이력 단일 생성
- 삭제 프로젝트의 일반 상세 및 하위 API 접근 차단
- 운영자 `includeDeleted` 조회와 조직장 권한 차단
- Cron이 삭제 프로젝트를 건너뜀
- 조직 제외의 이력 유무별 물리 삭제·비활성화
- 비활성 연결 재활성화 시 기존 이력 보존

### Web 테스트

- 제외 성공 후 활성 조직 목록에서 행 제거
- 제외된 조직이 추가 선택기에 다시 나타남
- 재추가 안내와 재활성화
- 종료 상태에서만 삭제 버튼 표시
- 정확한 이름 입력과 중복 제출 방지
- 삭제 목록 필터, 삭제 배지, 읽기 전용 상세와 복구
- 오류별 사용자 안내와 query 무효화

### E2E

- 조직 제외 후 목록에서 사라지고 다시 추가되는 흐름
- 프로젝트 종료, 이름 확인 삭제, 기본 목록 숨김
- 삭제 프로젝트 포함 필터 조회와 복구
- 복구된 프로젝트가 종료 상태로 일반 목록에 재등장

## 완료 기준

- 조직 제외가 성공하면 프로젝트 조직 목록에서 즉시 사라진다.
- 제외 조직을 다시 선택해 기존 연결과 이력을 복구할 수 있다.
- 종료 프로젝트만 이름 확인을 거쳐 소프트 삭제할 수 있다.
- 삭제 프로젝트는 일반 운영 API와 화면에서 숨겨진다.
- 운영자는 삭제 프로젝트를 조회하고 종료 상태로 복구할 수 있다.
- 삭제·복구의 데이터 변경과 감사 이력이 원자적으로 처리된다.
