# 새 참가자 일괄 명단 등록 설계

- 작성일: 2026-07-28
- 대상: `event-roster`
- 범위: 프로젝트 참가 명단의 `새 참가자` 등록

## 1. 배경과 목표

현재 참가자 추가 모달은 기존 참가자를 한 명 선택하거나 새 참가자의 이름과
소속 조직을 한 명씩 입력한다. 조직 담당자가 같은 조직 소속 여러 명을
등록하려면 모달을 반복해서 열어야 하므로 실제 명단 취합 흐름에 비해 작업량이
크다.

`새 참가자` 탭에서 한 조직을 선택하고 이름을 한 줄에 한 명씩 입력해 최대
30명을 한 번에 명단에 등록한다. 일괄 요청은 전부 성공하거나 전부 실패해야
한다. 이 기능에서 “초대”는 이메일, 알림 또는 계정 초대가 아니라 프로젝트
참가 명단 등록을 뜻한다.

## 2. 결정 사항

- 입력 방식은 줄바꿈으로 구분한 이름 목록이다.
- 모든 입력 참가자는 한 번의 요청에서 선택한 하나의 조직에 소속된다.
- 한 번에 1명 이상 30명 이하만 등록한다.
- 입력 목록 중 한 명이라도 등록할 수 없으면 아무도 등록하지 않는다.
- 입력 내부 또는 선택 조직의 참가자 마스터에 동명이인이 있으면 먼저
  경고하고, 사용자가 명시적으로 확인한 뒤에만 등록한다.
- 동명이인은 허용하므로 중복 이름을 영구적으로 차단하지 않는다.
- 기존 참가자 추가, 단건 새 참가자 추가 API의 기존 동작, Excel 가져오기는
  유지한다.
- 별도 D1 migration은 만들지 않는다.

## 3. 선택한 접근

### 3.1 전용 일괄 등록 API

`POST /api/v1/projects/:projectId/roster/bulk`를 추가한다. 프론트가 단건 API를
반복 호출하지 않고 이름 목록 전체를 한 요청으로 보낸다. Worker는 권한,
프로젝트와 조직 상태, revision, 중복 확인을 검증하고 D1의 원자적 batch 안에서
전체 참가자와 명단 행을 생성한다.

이 방식은 일부 참가자만 등록되는 상태를 만들지 않으며, 프로젝트 revision을
한 번만 증가시킨다.

### 3.2 제외한 접근

- 단건 API 반복 호출: 일부 성공을 피할 수 없고 요청 수만큼 revision이
  증가한다.
- Excel 가져오기 재사용: 이름 몇 개를 직접 넣는 작업에 파일 생성과 매핑
  단계가 추가돼 과도하다.

## 4. 사용자 화면

`참가자 추가` 모달의 `기존 참가자` 탭은 변경하지 않는다. `새 참가자` 탭은
다음 순서로 구성한다.

1. `소속 조직` 검색형 선택기
2. `이름` 여러 줄 입력란
3. 정리된 이름의 등록 예정 목록
4. 중복 경고 및 확인
5. 일괄 등록 버튼과 닫기 버튼

조직 선택기는 현재 프로젝트에 연결된 활성 조직만 표시하고 기존 최근 사용
조직 우선순위를 유지한다. 조직 선택 목록은 기존 Portal 기반 overlay를
재사용해 모달 내부 스크롤에 잘리지 않게 한다.

이름 입력란에는 `한 줄에 한 명씩 입력하세요`와 여러 줄 예시를 제공한다.
프론트는 각 줄의 앞뒤 공백을 제거하고 빈 줄을 제외한다. 정리 결과는 입력
아래에 번호가 있는 행으로 표시하고 `등록 예정 N명 / 최대 30명`을 함께
보여준다. 30명을 넘은 줄은 조용히 버리지 않고 초과 상태를 표시하며 등록
버튼을 비활성화한다.

등록 버튼의 문구는 상태에 따라 다음처럼 바뀐다.

- 유효한 이름 없음: `명단에 추가`, 비활성
- 유효한 이름 있음: `N명 명단에 추가`
- 요청 중: `N명 등록 중…`, 비활성

성공하면 모달을 닫고 프로젝트 데이터를 새로 불러온 뒤
`N명을 명단에 추가했습니다.`를 표시한다. 실패하면 모달, 이름 원문, 선택한
조직과 중복 확인 상태를 유지한다. 사용자가 이름이나 조직을 변경하면 이전
서버 중복 결과와 확인 상태를 폐기한다.

## 5. 입력 정규화와 중복 확인

서버가 최종 입력 정규화와 검증의 기준이다. 프론트도 같은 규칙을 사용해
즉각적인 미리보기를 제공하지만 프론트 결과만 신뢰하지 않는다.

저장할 이름은 다음 순서로 정리한다.

1. Unicode NFKC 정규화
2. 앞뒤 공백 제거
3. 이름 내부의 연속 whitespace를 ASCII 공백 하나로 축약

정리한 이름은 1자 이상 100자 이하여야 한다. 중복 비교용 키는 정리한 이름을
locale 독립적인 Unicode 소문자로 변환한 값이다. 표시와 저장에는 사용자가
입력한 대소문자를 보존한 정리 이름을 쓴다.

서버는 두 종류의 중복을 찾는다.

- `INPUT_DUPLICATE`: 같은 요청 안에서 비교용 이름 키가 두 번 이상 등장
- `EXISTING_PARTICIPANT`: 선택 조직의 참가자 마스터에 같은 비교용 이름 키가
  존재

중복이 있고 `confirmDuplicateNames`가 `false`이면 서버는 아무것도 변경하지
않고 HTTP 409 `CONFLICT`를 반환한다. `details`는 아래의 구조화된 정보를
포함한다.

```ts
{
  reason: "DUPLICATE_PARTICIPANT_NAMES";
  duplicates: Array<{
    name: string;
    kinds: Array<"INPUT_DUPLICATE" | "EXISTING_PARTICIPANT">;
  }>;
}
```

프론트는 중복 이름을 행 목록에 표시하고
`중복 이름을 확인했습니다` 체크박스를 보여준다. 사용자가 체크한 뒤 같은
입력에 `confirmDuplicateNames: true`를 보내면 동명이인을 포함해 등록한다.
입력 또는 조직이 바뀌면 체크는 자동 해제된다.

## 6. API 계약

요청은 strict schema이며 예상하지 않은 필드를 거부한다.

```ts
interface BulkRosterCreateRequest {
  organizationId: string;
  names: string[]; // 서버 정규화 후 1~30개, 각 1~100자
  confirmDuplicateNames: boolean;
  expectedRevision: number;
}
```

성공 응답은 생성 결과와 갱신된 프로젝트 revision을 반환한다.

```ts
interface BulkRosterCreateResponse {
  batchId: string;
  participants: Array<{
    participant: Participant;
    rosterEntry: RosterEntry;
  }>;
  projectRevision: number;
}
```

`names` 순서는 사용자가 입력한 순서를 보존하고 응답도 같은 순서를 유지한다.
각 참가자의 시스템 고유 ID와 공개 참가자 번호는 기존 단건 생성과 같은
방식으로 서버가 생성한다.

## 7. 권한과 프로젝트 상태

기존 새 참가자 단건 등록과 동일한 권한 규칙을 적용한다.

- 운영자는 프로젝트에 연결된 활성 조직에 등록할 수 있다.
- 조직 담당자는 자신의 담당 조직과 기존 프로젝트 상태 정책이 허용하는
  범위에서만 등록할 수 있다.
- 프로젝트 조직 연결 또는 조직 마스터가 비활성 상태면 거부한다.
- 종료된 프로젝트는 `PROJECT_CLOSED`로 거부한다.
- 요청의 `expectedRevision`이 현재 프로젝트 revision과 다르면
  `STALE_REVISION`으로 거부한다.

권한과 상태는 사전 조회뿐 아니라 원자적 쓰기의 guard에서도 다시 검사한다.
검사와 쓰기 사이에 상태가 바뀌어도 전체 요청은 실패한다.

`confirmDuplicateNames`가 `false`인 요청은 중복 검사 때 읽은 선택 조직의
참가자 수와 revision 합계도 guard에서 대조한다. 다른 프로젝트에서 같은 조직
참가자가 동시에 생성·수정되어 중복 판단의 기준 집합이 바뀌면
`STALE_REVISION`으로 전체 요청을 취소한다. 사용자는 갱신된 중복 결과를 보고
다시 결정한다.

## 8. 원자적 저장

Worker 서비스는 기존 Excel 가져오기의 제한된 multi-row SQL과
`runGuardedAtomic` 패턴을 재사용한다. D1 바인딩 수 제한을 넘지 않도록
참가자, 명단 행과 감사 로그 INSERT를 검증된 고정 크기로 나누되 모든
statement를 한 원자적 batch에 넣는다.

한 요청은 논리적으로 다음 변경을 만든다.

- `participants`: 입력 인원수만큼 생성
- `project_roster_entries`: 입력 인원수만큼 ACTIVE 행 생성
- `projects`: revision과 `updated_at` 한 번 갱신
- `audit_logs`: 참가자 생성과 명단 추가를 참가자마다 기록

모든 행은 하나의 `batchId`를 공유한다. 새 컬럼을 추가하지 않고 각 감사
로그의 `details_json`에 `batchId`, `projectId`, `organizationId`를 기록한다.
하나의 statement 또는 guard라도 실패하면 참가자, 명단, 감사 로그와 프로젝트
revision 변경을 모두 롤백한다.

프로젝트 상태에 따른 roster source, `was_expected_at_start`, 명단 snapshot은
기존 단건 등록 정책을 그대로 사용한다.

## 9. 오류 처리

- 중복 이름: 입력을 유지하고 중복 행과 확인 체크박스를 표시
- 30명 초과 또는 잘못된 이름: 해당 행과 제한을 표시하고 요청하지 않음
- `STALE_REVISION`: 최신 프로젝트 데이터를 다시 읽고 입력을 유지한 채 재시도
  안내
- `PROJECT_CLOSED`: 입력을 유지하고 종료되어 등록할 수 없다고 안내
- 조직 상태 또는 권한 변경: 조직을 다시 확인하도록 안내
- 예상하지 못한 실패: 전체가 등록되지 않았음을 명시하고 재시도 안내

응답이 성공하기 전에는 최근 사용 조직을 갱신하지 않는다. 성공한 공통 조직만
최근 조직의 최상단으로 이동한다.

## 10. 테스트 전략

### 계약

- 1명과 30명 요청 허용
- 빈 배열, 31명, 빈 이름, 100자 초과 이름, 잘못된 revision과 추가 필드 거부
- 중복 경고 details와 성공 응답 구조 검증

### Worker

- 1명과 30명의 참가자·명단 행 생성
- 입력 정규화와 입력 내부 중복 감지
- 선택 조직의 기존 참가자 동명이인 감지
- 확인 전 데이터 무변경, 확인 후 동명이인 생성
- 운영자와 조직 담당자 scope
- 비활성 또는 프로젝트에서 제외된 조직 거부
- 프로젝트 종료와 stale revision 거부
- 중간 statement 실패 시 전체 롤백
- 프로젝트 revision 정확히 1 증가
- 모든 감사 로그가 동일한 `batchId` 사용
- roster source, snapshot, `was_expected_at_start`가 단건 정책과 일치

### Web

- 줄바꿈 파싱, 공백 정리, 빈 줄 제거와 입력 순서 유지
- 등록 예정 인원과 30명 초과 상태 표시
- 중복 결과를 해당 행에 표시
- 입력 또는 조직 변경 시 중복 확인 초기화
- 확인 전 재요청 방지와 확인 후 요청 payload
- 요청 중 중복 클릭 방지
- 성공 메시지, 최근 조직 갱신과 모달 닫기
- 실패 시 모든 입력 유지
- 기존 참가자 탭 회귀 테스트

### 통합

- 같은 조직의 여러 새 참가자를 한 번에 등록하고 명단에서 모두 확인
- 서버 중복 경고를 확인한 뒤 동명이인을 등록
- 동시 revision 변경 시 아무도 추가되지 않음

## 11. 완료 기준

- 조직 담당자가 한 조직을 선택하고 최대 30명의 이름을 붙여넣어 한 번에
  등록할 수 있다.
- 부분 성공은 발생하지 않는다.
- 동명이인은 경고와 명시적 확인을 거쳐 등록할 수 있다.
- 프로젝트 revision과 감사 이력이 일괄 작업 단위로 추적 가능하다.
- 기존 단건 등록, 기존 참가자 추가와 Excel 가져오기에 회귀가 없다.
- D1 schema migration 없이 배포할 수 있다.
