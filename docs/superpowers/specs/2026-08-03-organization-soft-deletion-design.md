# 조직 소프트 삭제 설계

## 배경

현재 조직 삭제는 사용 중지된 조직에 연결된 담당자, 참가자, 프로젝트, 명단, 예상 인원 스냅샷이 하나도 없을 때만 물리 삭제할 수 있다. 실제 운영에서는 이미 사용된 조직도 관리 목록에서 제거하고 싶지만, 연결 지점을 일일이 해제하면 과거 행사 기록과 감사 가능성을 훼손할 수 있다.

조직 사용 중지는 일시적으로 신규 사용과 권한을 막았다가 다시 사용할 수 있는 상태로 계속 필요하다. 따라서 사용 중지와 삭제를 구분하면서도, 삭제된 조직을 복구할 수 있고 기존 기록을 보존하는 소프트 삭제를 도입한다.

## 목표

- 사용 중인 조직과 사용 중지된 조직을 연결 데이터 유무와 관계없이 삭제할 수 있다.
- 삭제 조직은 일반 목록, 조직 선택기, 신규 참가자 등록 등 일상적인 흐름에서 숨긴다.
- 담당자 배정, 참가자, 프로젝트 연결, 명단, 예상 인원 스냅샷과 감사 이력을 보존한다.
- 삭제된 조직을 복구할 수 있으며 복구 직후에는 사용 중지 상태로 둔다.
- 과거 프로젝트의 명단과 유의미한 집계에서는 삭제된 조직임을 표시하며 기록을 계속 제공한다.
- 조직 이름의 고유성을 삭제 후에도 유지해 동일 조직이 중복 생성되는 것을 막는다.
- 기존 조직 영구 삭제 경로를 제거한다.

## 비목표

- 삭제 조직의 연쇄 물리 삭제 또는 일정 기간 후 자동 삭제
- 과거에 이미 물리 삭제된 조직 복원
- 삭제와 동시에 담당자, 참가자 또는 프로젝트 연결 해제
- 조직 상태 모델 전체를 문자열 열거형으로 재구축
- 삭제 조직의 이름을 새 조직이 재사용하도록 허용

## 결정한 접근

`organizations`의 기존 `is_active` 의미를 유지하고 삭제 메타데이터를 별도로 추가한다. `ACTIVE`, `INACTIVE`, `DELETED` 열거형으로 전환하는 방식은 코드 전반의 활성 판정을 바꿔야 해 회귀 위험이 크다. 반대로 `is_active`만으로 삭제를 표현하면 사용 중지와 삭제를 구분할 수 없다.

따라서 다음 두 열을 추가한다.

- `deleted_at TEXT NULL`: 삭제 시각
- `deleted_by TEXT NULL REFERENCES users(id) ON DELETE RESTRICT`: 삭제한 운영자

상태는 다음과 같이 해석한다.

| 상태 | `is_active` | `deleted_at` | 의미 |
| --- | ---: | --- | --- |
| 사용 중 | 1 | `NULL` | 정상 사용 |
| 사용 중지 | 0 | `NULL` | 목록에 표시하며 다시 사용 가능 |
| 삭제됨 | 0 | 값 있음 | 일반 흐름에서 숨기고 복구 대상으로 관리 |

## 데이터 무결성과 생명주기

### 불변 조건

- 삭제된 조직은 반드시 `is_active = 0`이다.
- `deleted_at`과 `deleted_by`는 함께 설정되거나 함께 `NULL`이어야 한다.
- 삭제된 조직은 복구 이외의 이름, 활성 상태, 담당자, 프로젝트 연결 변경을 허용하지 않는다.
- 복구는 삭제 메타데이터만 제거하고 `is_active = 0`을 유지한다.
- 복구 후 운영자가 별도로 `다시 사용`을 실행해야 신규 등록과 기존 담당자 권한이 다시 활성화된다.
- `canonical_name` 고유 제약은 유지한다. 삭제 조직의 이름도 계속 점유한다.

마이그레이션에서는 열과 조회 인덱스를 추가하고, 가능한 범위에서 D1/SQLite 제약 또는 트리거로 삭제 메타데이터의 쌍과 삭제 시 비활성 조건을 강제한다. 서비스 계층에서도 같은 조건을 검증한다.

### 삭제

사용 중 또는 사용 중지 상태의 조직 모두 삭제할 수 있다. 삭제 요청은 다음 변경을 하나의 원자적 작업으로 수행한다.

1. 조직이 존재하며 아직 삭제되지 않았는지 확인한다.
2. 입력한 확인 이름이 현재 조직 이름과 정확히 일치하는지 확인한다.
3. 동시 변경이 없었는지 현재 이름, 정규화 이름, 활성 상태와 삭제 상태를 다시 검증한다.
4. `is_active = 0`, `deleted_at = now`, `deleted_by = actor`를 기록한다.
5. `ORGANIZATION_DELETED` 감사 이벤트를 기록한다.

기존 삭제 방해 조건과 물리 `DELETE` 문은 제거한다. 프로젝트 연결, 참가자, 담당자 배정, 명단과 스냅샷은 변경하지 않는다.

### 복구

복구 요청은 다음 변경을 원자적으로 수행한다.

1. 조직이 삭제된 상태인지 확인한다.
2. 동시 복구 또는 변경이 없었는지 삭제 메타데이터를 다시 검증한다.
3. `deleted_at`과 `deleted_by`를 `NULL`로 바꾸고 `is_active = 0`을 유지한다.
4. `ORGANIZATION_RESTORED` 감사 이벤트를 기록한다.

복구된 조직의 담당자 배정과 프로젝트 연결은 보존되어 있지만, 사용 중지 상태이므로 권한과 신규 등록은 계속 차단된다. 기존 상태 변경 API로 `다시 사용` 처리한 뒤 기존 담당자 권한이 다시 적용된다.

## API와 계약

### 조직 표현

관리자용 조직 요약과 상세 계약에는 삭제 상태를 판별할 필드를 추가한다. UI가 날짜를 표시할 수 있도록 최소한 다음 정보를 제공한다.

- `isDeleted: boolean`
- `deletedAt: string | null`

삭제 수행자 상세 정보는 감사 이력에서 확인할 수 있으므로 기본 조직 응답에 사용자 정보를 중복 확장하지 않는다. 서버 내부에서는 `deleted_by`를 보존한다.

### 엔드포인트

- `DELETE /organizations/:id`
  - 기존 영구 삭제 엔드포인트를 소프트 삭제 의미로 변경한다.
  - 본문은 기존처럼 정확한 `confirmationName`을 요구한다.
  - 성공 시 `204 No Content`를 반환한다.
- `POST /organizations/:id/restore`
  - 삭제 조직을 사용 중지 상태로 복구한다.
  - 기존 프로젝트 복구 API와 같은 관례로 갱신된 조직을 JSON으로 반환한다.
- 조직 목록
  - 기본 조회에서는 삭제 조직을 제외한다.
  - 관리 운영자용 `includeDeleted` 조건으로 삭제 조직을 포함할 수 있다.
- 조직 상세
  - 관리 운영자는 삭제 조직을 직접 조회할 수 있다.
  - 조직 담당자와 일반 프로젝트 흐름에서는 삭제 조직을 활성 조직으로 취급하지 않는다.

`includeDeleted`는 관리 운영자에게만 허용한다. 삭제된 조직의 직접 URL 조회도 동일한 관리 권한을 요구한다.

### 오류와 동시성

- 삭제된 조직 재삭제: `409 Conflict`
- 삭제되지 않은 조직 복구: `409 Conflict`
- 확인 이름 불일치: `409 Conflict`
- 삭제·복구 도중 조직 상태가 바뀜: `409 Conflict`
- 삭제 조직 수정, 활성화, 담당자 변경, 프로젝트 연결 변경: `409 Conflict`
- 삭제 조직과 같은 정규화 이름으로 생성: 구조화된 이름 충돌 오류

조직 생성 시 삭제 조직과의 이름 충돌을 일반 중복과 구분할 수 있는 오류 정보를 제공한다. 관리 UI는 새 조직 생성을 반복하도록 두지 않고 해당 삭제 조직의 상세 또는 삭제 조직 보기로 안내한다.

현재 조직 변경 서비스에서 사용하는 원자적 운영자 가드를 재사용한다. 삭제·복구의 상태 변경과 감사 기록은 반드시 같은 원자적 실행에 포함한다.

## 권한

- 삭제와 복구는 비부트스트랩 `OPERATOR`, 즉 기존 `requireAdministrativeOperator`를 통과한 계정만 수행할 수 있다.
- 부트스트랩 계정과 `ORGANIZATION_MANAGER`는 삭제·복구할 수 없다.
- 삭제 조직에 배정된 대표 조직장과 추가 담당자는 배정 데이터를 유지하지만 조직 권한을 사용할 수 없다.
- 복구 직후에도 조직이 사용 중지 상태이므로 담당자 권한은 비활성이다.
- 조직이 다시 사용 상태가 되면 기존 배정을 기반으로 권한이 복원된다.

모든 조직 범위 권한 판정은 조직이 삭제되지 않았고 활성 상태인지 확인해야 한다. 단순히 `is_active`만 검사하는 경로가 남지 않도록 서비스와 조회를 점검한다.

## 조회와 과거 기록

### 일반 운영 흐름

삭제 조직은 다음 위치에서 제외한다.

- 기본 조직 목록
- 프로젝트에 조직을 추가하는 검색과 선택기
- 참가자 추가·수정의 조직 선택기
- 엑셀 가져오기 대상 조직 검증
- 조직 담당자가 접근 가능한 조직 목록과 프로젝트 범위

### 프로젝트 기록

삭제 전에 생성된 명단 행은 조직명 스냅샷을 사용하므로 그대로 표시한다. 프로젝트 조직별 집계는 기존의 기록 보존 규칙을 확장한다.

- 삭제 조직에 예상, 추가, 취소 또는 실제 인원 기록이 하나라도 있으면 집계에 포함한다.
- 기록이 전혀 없는 삭제 조직 연결은 집계에서 숨긴다.
- 표시되는 삭제 조직에는 `삭제됨` 배지를 붙인다.
- `사용 중지` 또는 프로젝트 내 제외와 `삭제됨`을 구분한다.

이를 위해 프로젝트 조직 및 요약 계약에 마스터 조직의 삭제 여부를 전달하고, 화면의 기존 `비활성` 배지 판정을 삭제 상태와 분리한다. 원본 참가자와 프로젝트 연결은 삭제하지 않는다.

## 관리자 UI

### 조직 목록

- 기본값은 삭제 조직 제외이다.
- 관리 운영자에게 `삭제된 조직 보기` 필터를 제공한다.
- 삭제 조직에는 `삭제됨` 배지를 표시하고 상세 화면으로 이동할 수 있게 한다.
- 사용 중, 사용 중지, 삭제됨은 서로 다른 상태로 표현한다.

### 삭제 확인

조직 상세의 기존 영구 삭제 패널과 삭제 방해 조건 표시는 제거하고 복구 가능한 `조직 삭제` 흐름으로 교체한다.

확인 모달은 다음 내용을 안내한다.

- 조직이 일반 목록과 선택기에서 숨겨진다.
- 사용 중 조직이면 자동으로 사용 중지된다.
- 담당자, 참가자, 프로젝트와 감사 기록은 보존된다.
- 나중에 복구할 수 있다.

사용자는 현재 조직 이름을 정확히 입력해야 최종 삭제 버튼을 누를 수 있다. 성공 후에는 조직 목록으로 이동한다.

### 삭제 조직 상세와 복구

삭제 조직 상세는 읽기 전용이다.

- 상단에 `삭제됨` 상태와 삭제 시각을 표시한다.
- 조직명, 기존 담당자, 연결 프로젝트와 변경 이력을 조회할 수 있다.
- 이름, 활성 상태, 담당자, 프로젝트 연결 변경 동작을 숨기거나 비활성화한다.
- 주요 변경 동작으로 `조직 복구`만 제공한다.

복구 후 상세 화면은 `사용 중지` 상태를 보여주며, 운영자가 필요할 때 별도로 `다시 사용`을 선택한다.

### 삭제 조직과 같은 이름 생성

조직 생성 요청이 삭제 조직 이름과 충돌하면 다음을 표시한다.

- `삭제된 동일 이름의 조직이 있습니다` 안내
- 해당 삭제 조직 상세 또는 삭제 조직 보기로 이동하는 동작
- 새 조직 생성은 수행하지 않음

## 감사 이력

다음 이벤트를 추가하거나 기존 이벤트 의미를 변경한다.

- `ORGANIZATION_DELETED`
- `ORGANIZATION_RESTORED`

각 이벤트에는 수행자, 대상 조직, 수행 시각과 상태 전후를 기록한다. 삭제 이벤트의 `after`는 조직 자체가 사라진 것으로 표현하지 않고 `isActive: false`, 삭제 메타데이터가 설정된 상태로 기록한다. 복구 이벤트는 삭제 메타데이터가 해제되고 비활성 상태로 남았음을 기록한다.

기존 `조직 사용 중지`와 `조직 다시 사용` 감사 이벤트는 유지한다.

## 테스트 전략

### 도메인과 DB

- 활성 조직과 비활성 조직 모두 삭제 가능
- 삭제 시 자동 비활성화와 삭제 메타데이터 기록
- 복구 후 비활성 상태 유지
- 삭제와 복구의 중복·경합 요청 충돌
- 삭제 조직 이름 재사용 차단과 구조화된 오류
- 담당자, 참가자, 프로젝트 연결, 명단과 예상 스냅샷 보존
- 삭제·복구와 감사 로그의 원자성
- DB 불변 조건 위반 차단

### 권한

- 관리 운영자의 삭제·복구 허용
- 부트스트랩과 조직 담당자의 삭제·복구 거부
- 삭제 조직 담당자의 범위 권한 거부
- 복구 직후 권한 거부
- 재활성화 후 기존 담당자 권한 복원

### UI

- 기본 목록에서 삭제 조직 숨김
- 삭제 조직 보기 필터와 상태 배지
- 정확한 이름을 요구하는 삭제 모달
- 삭제 상세 읽기 전용 처리와 복구
- 동일 이름 생성 시 복구 안내
- 프로젝트 명단과 유의미한 집계의 `삭제됨` 표시
- 기록이 없는 삭제 조직 집계 제외

### 회귀 검증

- 전체 단위·통합 테스트
- 타입 검사
- 린트
- 프로덕션 빌드
- 새 D1 마이그레이션을 적용한 로컬 DB 검증

## 배포와 운영

1. 로컬 D1 마이그레이션과 전체 검증을 완료한다.
2. 원격 D1에 새 마이그레이션을 적용한다.
3. Worker를 재배포한다.
4. 운영 환경에서 기본 목록, 삭제 조직 보기, 삭제, 복구와 과거 프로젝트 표시를 확인한다.

열 추가는 기존 조직을 모두 삭제되지 않은 상태로 유지한다. 과거 영구 삭제로 이미 물리 제거된 조직은 원본 데이터가 없으므로 이번 마이그레이션으로 복원하지 않는다. 배포 이후 조직 물리 삭제 경로는 제공하지 않는다.

## 수용 기준

- 연결 데이터가 있는 사용 중 조직도 이름 확인 후 삭제할 수 있다.
- 삭제 후 조직이 일반 관리 목록과 모든 신규 선택기에서 사라진다.
- 삭제된 조직의 기존 참가자, 프로젝트, 담당자와 감사 기록이 유지된다.
- 과거 프로젝트의 기록이 있는 조직은 `삭제됨` 표시와 함께 집계·명단에 남는다.
- 관리 운영자가 삭제 조직을 찾아 복구할 수 있다.
- 복구된 조직은 비활성이며, 재활성화 전에는 담당자 권한과 신규 등록이 차단된다.
- 재활성화하면 기존 담당자 배정이 다시 동작한다.
- 삭제 조직과 같은 이름으로 새 조직을 만들 수 없으며 복구 경로를 안내한다.
- 조직 영구 삭제 API와 UI가 남아 있지 않다.
