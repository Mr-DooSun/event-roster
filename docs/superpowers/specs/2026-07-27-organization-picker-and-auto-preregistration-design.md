# 조직 선택 오버레이와 프로젝트 자동 사전 등록 설계

## 1. 목표

이 변경은 서로 독립적인 두 가지 사용성 문제를 해결한다.

1. 참가자 추가 모달의 조직 검색 결과가 모달 스크롤 영역에 잘리지 않게
   표시하고, 최근 사용 조직을 빠르게 다시 선택할 수 있게 한다.
2. 프로젝트 생성 직후 별도의 `사전 등록 시작` 조작 없이 참가자 명단을
   등록할 수 있게 한다.

예상 인원과 행사 당일 증감을 구분하는 기존 집계 모델은 유지한다. 프로젝트는
생성 즉시 사전 등록 상태가 되고, 행사 당일 운영자가 `진행 시작`을 눌렀을 때
예상 명단 스냅샷을 만든다.

## 2. 범위

### 포함

- 참가자 추가 모달의 조직 목록을 React Portal 오버레이로 렌더링
- 가용 공간에 따른 목록의 위·아래 자동 배치
- 프로젝트·사용자별 최근 조직 3개 브라우저 저장
- 검색 결과의 최근 조직 우선 정렬
- 새 참가자 모드의 최근 조직 기본 선택
- 프로젝트 생성 상태를 `PRE_REGISTRATION`으로 변경
- 기존 `PREPARING` 프로젝트를 `PRE_REGISTRATION`으로 전환
- `준비 중` UI와 `사전 등록 시작` 동작 제거
- 관련 단위·통합·E2E 회귀 테스트와 운영 배포 검증

### 제외

- 최근 조직의 서버 저장 또는 여러 브라우저 간 동기화
- 조직 사용 통계나 즐겨찾기 기능
- 예상/실제/증감 집계 모델 변경
- 행사 진행 중 조직 담당자의 수정 권한 확대
- DB CHECK 제약에서 `PREPARING` 문자열을 즉시 제거하기 위한 테이블 재생성

## 3. 조직 선택 오버레이

### 3.1 컴포넌트 경계

`OrganizationSelectCombobox`는 검색어, 확정 선택 ID, 키보드 활성 옵션을
계속 관리한다. 목록 렌더링만 `document.body` 아래의 Portal로 이동한다.

위치 계산은 별도의 작은 hook 또는 순수 계산 함수로 분리한다. 이 단위는 다음
입력을 받는다.

- 입력창의 `DOMRect`
- viewport 너비와 높이
- 원하는 목록 최대 높이
- 입력창과 목록 사이 간격

출력은 `top`, `left`, `width`, `maxHeight`, `placement`다. 아래쪽 공간이
목록의 최소 표시 높이를 충족하면 아래에 배치하고, 그렇지 않으면 위쪽 공간을
사용한다. 양쪽 모두 부족하면 더 넓은 쪽을 선택하고 목록 내부를 스크롤한다.

### 3.2 레이어와 위치 갱신

- 목록은 모달 backdrop보다 높은 전용 z-index를 사용한다.
- 목록은 viewport 좌표를 사용하는 `position: fixed` 레이어로 배치한다.
- 입력창 너비와 같은 너비를 기본값으로 사용하되 viewport 밖으로 나가지
  않도록 좌우 위치를 제한한다.
- 목록이 열린 동안 window `resize`와 capture 단계 `scroll` 이벤트에서
  위치를 다시 계산한다.
- 입력창이나 목록이 DOM에서 제거되면 목록을 닫는다.
- 목록 외부 클릭, blur, Escape 동작은 기존 계약을 유지한다.
- 첫 Escape는 열린 목록만 닫고, 목록이 닫힌 뒤 Escape는 상위 모달을 닫는다.
- Portal 안의 옵션 클릭은 모달의 focus trap과 충돌하지 않아야 한다.
- 외부 클릭 판정은 입력 컨테이너와 Portal 목록 ref를 모두 내부 영역으로
  취급한다.

## 4. 최근 조직

### 4.1 저장 범위와 형식

최근 조직은 브라우저 `localStorage`에 저장한다. 저장 키는 스키마 버전,
로그인 사용자 ID, 프로젝트 ID를 포함한다.

예:

```text
event-roster:recent-organizations:v1:<user-id>:<project-id>
```

값은 최신순 조직 ID 배열이며 최대 3개만 유지한다. 조직 이름이나 사용자
정보는 저장하지 않는다.

저장소 읽기·쓰기 실패, JSON 손상, 배열이 아닌 값은 빈 기록으로 처리한다.
이 실패가 참가자 등록이나 일반 조직 검색을 막아서는 안 된다.

### 4.2 기록 시점

최근 기록은 참가자 추가 API가 성공하고 최신 프로젝트 데이터를 다시 불러온
뒤에만 갱신한다.

- 새 참가자 생성 후 명단 추가 성공
- 기존 참가자 확인 후 명단 추가 성공

입력만 변경한 경우, 모달을 닫은 경우, API가 실패하거나
`STALE_REVISION`을 반환한 경우에는 기록하지 않는다.

### 4.3 정렬과 기본값

- 활성 상태이며 현재 프로젝트에 연결된 조직만 후보로 사용한다.
- 최근 배열에 없는 조직은 서버가 제공한 기존 순서를 유지한다.
- 검색어가 있거나 없거나, 검색 조건을 만족한 최근 조직을 먼저 배치한다.
- 최근 조직 사이에서는 최신순을 유지한다.
- 비활성화되거나 프로젝트에서 제외된 ID는 결과와 기본값에서 제외하고 다음
  저장 시 정리한다.

새 참가자 모드를 열 때 가장 최근의 유효한 조직을 기본 선택한다. 유효한 최근
조직이 없으면 현재와 같이 첫 번째 활성 조직을 사용한다.

기존 참가자 모드는 참가자에게 저장된 현재 조직을 그대로 선택한다. 최근
기록은 목록 정렬에만 사용하며 확정 조직을 자동 변경하지 않는다.

## 5. 프로젝트 자동 사전 등록

### 5.1 사용자 수명주기

사용자에게 보이는 수명주기는 다음과 같다.

```text
프로젝트 생성 → 사전 등록 → 진행 중 → 종료
```

- 프로젝트 생성 API는 새 행을 `PRE_REGISTRATION`으로 만든다.
- 프로젝트 카드와 상세 화면에서 `준비 중` 상태를 더 이상 만들거나 안내하지
  않는다.
- `사전 등록 시작` 버튼과 `PREPARING → PRE_REGISTRATION` 전환 요청을
  제거한다.
- 행사 당일 운영자가 `진행 시작`을 누르면 기존과 동일하게 예상 명단
  스냅샷을 만들고 상태를 `IN_PROGRESS`로 전환한다.
- `IN_PROGRESS → CLOSED`, 자동 종료, `CLOSED → IN_PROGRESS` 재개 정책은
  유지한다.

### 5.2 기존 데이터 migration

새로운 append-only D1 migration은 모든 `PREPARING` 프로젝트를
`PRE_REGISTRATION`으로 변경한다. 각 행의 revision을 증가시키고
`updated_at`을 migration 실행 시각으로 갱신해 stale client가 이전 revision으로
변경하지 못하게 한다. 같은 migration에서 actor가 없는 시스템 감사 이벤트를
프로젝트별로 남겨 운영자가 자동 전환 사실과 시각을 확인할 수 있게 한다.

DB CHECK 제약에는 한 번의 호환 기간 동안 `PREPARING`을 남긴다. 서비스와
UI는 새 `PREPARING` 값을 생성하거나 전환 대상으로 허용하지 않는다. 테이블
재생성을 통한 CHECK 축소는 별도 정리 작업으로 남긴다.

migration 전에는 운영 runbook에 따라 원격 D1 export와 checksum을 만들고,
적용 후 다음을 검증한다.

- `status = 'PREPARING'` 행이 0개
- 변환된 행이 모두 `PRE_REGISTRATION`
- `PRAGMA foreign_key_check` 결과가 비어 있음

### 5.3 권한과 명단 의미

- `PRE_REGISTRATION`에서는 운영자와 해당 프로젝트에 배정된 활성 조직
  담당자가 기존 정책대로 명단을 변경할 수 있다.
- 엑셀 가져오기는 `PRE_REGISTRATION`에서만 허용한다.
- `진행 시작` 시점의 활성 사전 명단을 예상 인원으로 고정한다.
- `IN_PROGRESS`에서는 운영자만 당일 추가·취소·수정을 수행하고 조직 담당자는
  읽기 전용이다.
- `CLOSED`에서는 기존과 같이 변경을 거부한다.

## 6. 오류와 동시성

- Portal 위치 계산 실패 시 목록은 입력창 아래에 viewport 제한 높이로
  표시한다.
- 브라우저 저장 실패는 사용자에게 치명적 오류로 표시하지 않고 최근 기능만
  비활성화한다.
- 참가자 추가 실패 시 모달과 현재 입력값을 유지하고 최근 기록은 갱신하지
  않는다.
- 후보 조직이 갱신되어 선택된 조직이 사라지면 선택 ID를 비우고 제출을
  차단한다.
- 프로젝트 상태 전환과 명단 mutation은 기존 revision guard와 D1 batch
  원자성을 유지한다.
- migration과 동시에 이전 클라이언트가 요청해도 증가한 project revision과
  허용 상태 검사로 stale 변경을 거부한다.
- 상태 전환 API는 `PREPARING`을 새 target으로 받지 않으며, 호환용 enum 값이
  남아 있더라도 서비스가 새 `PREPARING` 행을 만들 수 없게 한다.

## 7. 테스트 전략

### 7.1 조직 선택

- 목록이 `document.body` Portal 아래에 렌더링되는지 검증
- 아래 공간 부족 시 위로, 충분할 때 아래로 배치되는 순수 계산 테스트
- resize·scroll 시 좌표 갱신 테스트
- 외부 클릭, blur, Tab, Arrow, Enter, 연속 Escape와 ARIA 계약 테스트
- 후보가 열린 동안 축소될 때 active option을 유효 범위로 초기화하는 테스트
- 최근 조직의 사용자·프로젝트 격리, 최대 3개, 중복 제거, 손상 데이터 복구
  테스트
- 검색 결과에서 최근 조직 우선 정렬 테스트
- 성공한 추가만 기록하고 실패·stale 요청은 기록하지 않는 통합 테스트
- 새 참가자 기본 선택과 기존 참가자 현재 조직 보존 테스트

### 7.2 프로젝트 수명주기

- 생성 응답이 곧바로 `PRE_REGISTRATION`인지 검증
- 서비스가 `PREPARING` 전환을 더 이상 노출하지 않는 계약·도메인 테스트
- migration이 기존 `PREPARING` 행, revision, updated_at을 올바르게
  변환하는 통합 테스트
- 생성 직후 명단 등록·엑셀 가져오기·조직 담당자 수정이 가능한지 검증
- `진행 시작` 스냅샷과 예상/실제/증감 집계가 기존과 동일한지 검증
- 진행 중 조직 담당자 읽기 전용과 종료 프로젝트 변경 거부 회귀 테스트

### 7.3 전체 검증

- 포맷 검사와 전체 TypeScript 검사
- 전체 단위·Worker 통합 테스트
- Web production build
- Chromium E2E
- Worker deploy dry-run과 D1 migration 검증

## 8. 구현 순서

1. 프로젝트 생성 상태와 legacy `PREPARING` migration을 먼저 구현한다.
2. 수명주기 UI와 권한·집계 회귀 테스트를 정리한다.
3. 최근 조직 저장·정렬을 순수 유틸리티로 구현한다.
4. 조직 목록 Portal과 위치 계산을 구현한다.
5. 참가자 추가 성공 흐름에 최근 기록과 기본 선택을 연결한다.
6. 전체 검증과 접근성·반응형 리뷰를 수행한다.
